# SWInv — сценарій демонстрації (12–15 хв)

Мета: за чверть години показати, що (1) ПЗ збирається «до пакетів», (2) n8n + AI зіставляють пакети з продуктами й категоріями, (3) результат прогнозований, а довідники оновлюються коректно і з аудитом. Кожен блок має свій «ага-момент» — те, що глядач має побачити на екрані власними очима.

## 1. Сценарій

### (a) Дашборд і числа — 1,5 хв

Вкладка 1. Пройти зверху вниз, не читаючи все:

Клік по хосту фільтрує всі картки нижче і додає блок «Зміни на хості за останній збір» (нові / змінили версію / зникли). Довідники, правила й черга перевірки спільні для всього парку.
- KPI: **1 хост · 562 пакети · ≈ 298 продуктів · покриття ~100 % · частка рішень AI · заборонених / обмежених · у черзі перевірки · довідники (продуктів / вендорів / правил)**.
- Таблиця «Запуски інвентаризації»: перший запуск — `Правила 324`, `AI 69`, `Звернень до AI 7`, `Змін довідників 788`, 66 с. Другий — **зелений рядок**: `0 / 0 / 0`, `Відомі до запуску 393` (один відбиток чекає на людину), `Звернень до AI 0`, `Змін довідників 0`.
- Картка «Хто прийняв рішення»: більшість пакетів закрили правила й довідник, AI — меншість.
- «Продукти з найбільшою кількістю пакетів»: **Microsoft Visual C++ Redistributable — 23 пакети → 1 продукт**, SQL Server 21 → 1, Windows SDK 16 → 1, Python 11 → 1.

> **Ага-момент:** «562 пакети перетворились на ~298 продуктів із категоріями, і при повторному запуску система не зробила жодного зайвого руху».

Фраза для переходу: «Тепер покажу, як саме це працює всередині».

### (b) Канвас воркфлоу 1 по смугах — 2 хв

Вкладка 2. П'ять кольорових sticky-нотаток = п'ять смуг, читати їх заголовки зліва направо:

1. **Приймання та нормалізація** — `Webhook: POST /inventory/ingest` (Header Auth) → `Валідація payload` → `Нормалізація (norm_v1)` → дві SQL-ноди → `Відповідь колектору (202 Accepted)`. Наголосити: відповідь колектору йде одразу, класифікація — асинхронно.
2. **Детерміноване зіставлення — БЕЗ AI** — `БД: крок 1 — точні збіги (довідник)` → `БД: крок 2 — правила (dict_rules)`. Кожна нода — один `SELECT swinv_…()`; логіка в Postgres, атомарна, тестується в psql.
3. **AI лише для невідомого** — `Пакетування (по 10, відсортовано)` → `Цикл по батчах` → `Промпт для AI` → `AI: класифікація (Basic LLM Chain)` з під-нодами `Ollama Chat Model (локально, GPU)` і `Структурований вивід (JSON Schema)`; поруч сіра `OpenAI Chat Model (альтернатива, вимкнено)`. Відкрити `Промпт для AI` і показати, що перелік категорій береться з ноди `Довідник категорій`, а не захардкоджений.
4. **Запис у довідники з пріоритетами** — `Валідація відповіді AI` → `Відповідь валідна?` → `БД: запис результатів AI (пріоритет ai=100)` / `БД: батч у чергу перевірки (AI недоступний / невалідно)`. Відкрити валідацію: видно пороги `0.80 / 0.60`, echo-back id, закритий перелік.
5. **Фіналізація** — `БД: фіналізація запуску (лічильники)` → `Підсумок запуску`.

> **Ага-момент:** «AI — третій крок, а не перший; і між AI та довідником стоїть детермінований валідатор».

### (h) Очікувані питання і короткі відповіді — решта часу

**«Як ви гарантуєте, що AI не вигадає категорію чи продукт?»**
Категорію — ніяк не може: перелік іде з `dict_category` у промпт, JSON Schema парсера містить `enum` кодів, валідатор ще раз звіряє з довідником, а `UNKNOWN` — легальна відповідь «не знаю» (так сталося з Preptail). Продукт — може назвати неточно, тому: пороги впевненості, черга перевірки, найнижчий пріоритет запису (`ai = 100`), аудит і людина, яка виправляє один раз і назавжди.

**«Що буде, якщо запустити двічі? А якщо оновилась версія програми?»**
Двічі — 0/0/0, 0 звернень до AI, 0 змін довідників (щойно бачили). Нова версія — `changed = 1`, але відбиток без версії той самий, тому продукт відомий, AI не викликається; попередня версія зберігається в `version_prev`.

**«Що буде, якщо Ollama впаде посеред запуску?»**
Нода LLM робить 2 спроби з паузою 3 с, потім error-вихід → `swinv_ai_failed`: весь батч у чергу з причиною `ai_unavailable`, запуск завершується зі статусом `done` і чесним `unresolved`. Наступний запуск автоматично повторює лише такі технічні збої (`swinv_unresolved`), а при успіху закриває старі записи черги з `resolved_by = ai-retry`. Помилки самого воркфлоу ловить воркфлоу 4 і пише в `audit_log`.

**«Правило додали пізніше — а що зі старими рішеннями AI?»**
Звичайний запуск чіпає лише нові відбитки, тому є перекласифікація: `POST /webhook/inventory/reclassify` (воркфлоу 5) застосовує поточні правила до всього парку заднім числом і перекриває рішення `ai`/`exact`, але не `human`/`seed`. Рішення людини з форми робить це автоматично: створене правило одразу проганяється по всіх хостах. Перевірено: правило для Mobalytics перекрило рішення AI (`ai → rule`, запис в аудиті з актором `reclassify`), а конфліктне правило для Preptail не змогло перекрити рішення людини.

**«А якщо скинути базу — модель відповість так само?»**
Чесна відповідь із числами: `reclassify` з `reset_ai` видалив 68 рішень AI, збір запитав модель повторно, звіт `/webhook/inventory/api/consistency` показав збіг категорії 95,6 % і назви продукту 82,4 %. Розбіжності — це «Gothic 2» проти «Gothic II», «Twilio CLI» проти «twilio-cli». Тому канонічну назву й категорію фіксує довідник, а не модель; модель — джерело пропозицій. Плюс echo-back назви пакета у валідаторі відсікає переплутані рядки всередині батчу.

**«Як додати категорію?»**
Два місця: `INSERT INTO dict_category (code, name_uk, name_en, description, policy, sort_order)` — і вона одразу з'являється в промпті, формі та дашборді; плюс додати код у `CATEGORY_CODES` у `n8n/build_workflows.py` (enum JSON Schema), виконати `python n8n/build_workflows.py` і повторно `setup.ps1` (імпорт ідемпотентний). Якщо забути друге — парсер відхилить відповіді з новим кодом і батч піде в чергу: безпечна відмова, але шумна.

**«Як масштабувати на парк ПК?»**
Колектор — scheduled task через GPO/Intune з `-WebhookUrl` центрального n8n; хости розрізняються за `machine_id`, пакети — за `(host_id, source, source_key)`. Довідники спільні: другий ПК з тим самим офісним набором майже не породжує звернень до AI — питають лише про унікальне для нього. n8n у queue-режимі з воркерами, Ollama з `OLLAMA_NUM_PARALLEL` > 1 або кілька інстансів. Дашборд уже групує по хостах (`v_software_by_host`).

**«Чому логіка в Postgres-функціях, а не в 40 нодах n8n?»**
Атомарність (крок = одна транзакція), швидкість (562 пакети одним set-based запитом замість 562 ітерацій), тестованість у psql без n8n, версіонування в git, і аудит-тригер, який не можна обійти з воркфлоу. n8n лишається читабельним оркестратором: 5 смуг, кожна SQL-нода — один `SELECT swinv_…()`. Low-code не означає «без SQL» — означає, що бізнес-логіку видно і її можна змінити без деплою.

**«Чому локальна модель, а не GPT?»**
Дані про ПЗ робочих станцій — внутрішня інформація. Локальна 14B-модель за наявності GPU дає ~9 с на батч і достатню якість для класифікації з валідатором зверху. Хмарна — одна нода поруч, якщо ІБ погодить.

**«Скільки коштує звернення до AI?»**
На першому запуску — 8 батчів на 562 пакети; далі — лише нове. Вартість прямує до нуля разом із наповненням довідника.

## 2. Прибирання після демо

```powershell
reg delete "HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\SWInvDemoApp" /f
powershell -NoProfile -ExecutionPolicy Bypass -File .\collector\Collect-Inventory.ps1
```

Наступний запуск покаже `diff: {added: 0, changed: 0, removed: 1}`: пакет отримує `present = false` і `removed_at`, зникає з поточного реєстру і KPI, але запис у `dict_package_map` залишається — довідник пам'ятає рішення, і якщо програма з'явиться знову (на цьому чи іншому ПК), AI про неї вже не питатимуть.

Якщо під час (f) змінювали політику — переконатися, що `REMOTE_ACCESS` повернуто в `restricted`.
